# WSL 协作说明

这份说明是给 WSL Ubuntu 里的 AI 或接手者看的。

当前协作方式不是“在 WSL 里开发并直接在 WSL 里跑真机”，而是：

1. 在 WSL 里阅读、分析、修改代码。
2. 修改完成后，把改动同步回这台比赛机器。
3. 所有真机相关启动、ROS 联调、相机验证、机械臂动作、吸泵动作、底盘运行，默认都在这台机器上执行，不在 WSL 里执行。

## 1. 当前目录映射

这台机器上的原始工程根目录是：

- /home/eaibot

WSL 侧用于看代码和改代码的镜像目录是：

- /home/zcy/eaibot

WSL 侧已经拷贝过去的重点内容应包括：

- /home/zcy/eaibot/zcy
- /home/zcy/eaibot/robocom_ws/src
- /home/zcy/eaibot/mirobot_ws/src
- /home/zcy/eaibot/handeye-calib/src

因此你在 WSL 里看到的代码路径，和真机上的路径结构基本一致，只是根目录从 /home/eaibot 变成了 /home/zcy/eaibot。

处理路径时要始终注意这一点。

## 2. 你的工作边界

你在 WSL 里的主要职责是：

1. 阅读工程结构。
2. 找到真正控制行为的代码入口。
3. 修改源码、launch、yaml、脚本或说明文档。
4. 给出最小验证步骤。
5. 明确说明哪些步骤必须回到真机执行。

你不应该默认在 WSL 里做这些事：

1. 直接启动真机机械臂。
2. 直接启动真实 Astra 相机、雷达、底盘串口、吸泵串口。
3. 假设 WSL 中一定具备 ROS 驱动、USB 透传、图形界面、MoveIt 真机链路。
4. 把 WSL 当成最终运行环境。

默认判断原则：

- 能离线完成的事，在 WSL 做。
- 依赖真实硬件、真实串口、真实相机、真实 ROS 设备链路的事，在这台机器做。

## 3. 你修改后必须遵守的同步规则

WSL 里的修改不是最终生效点。

真正运行用的是这台机器上的原始工程，所以：

1. 你在 WSL 修改完后，必须把改动同步回 /home/eaibot 对应目录。
2. 不能只改 /home/zcy/eaibot 而不同步，否则真机运行看到的还是旧代码。
3. 如果改动涉及多个工作区，必须保证对应多个工作区都同步回去。

最常见同步目标：

- /home/zcy/eaibot/robocom_ws/src -> /home/eaibot/robocom_ws/src
- /home/zcy/eaibot/mirobot_ws/src -> /home/eaibot/mirobot_ws/src
- /home/zcy/eaibot/handeye-calib/src -> /home/eaibot/handeye-calib/src
- /home/zcy/eaibot/zcy -> /home/eaibot/zcy

如果只改了单个文件，也要明确告诉用户需要同步哪个文件。

## 4. 路径修改时的硬约束

很多旧代码里直接写死了 /home/eaibot 路径。

因此在 WSL 阅读或临时验证时，看到这类路径不要立刻认定为错误，要先区分两种情况：

1. 这是给真机运行时用的真实路径。
2. 这是为了兼容当前比赛机器环境而故意写死的路径。

如果代码最终还是要回到这台机器执行，那么很多 /home/eaibot 的硬编码不一定要改。

除非用户明确要求把代码改成双环境兼容，否则不要为了“让 WSL 本地跑通”而大量改路径。

更稳妥的做法是：

1. 优先保留真机路径语义。
2. 必要时把路径改成“可配置”，例如优先读参数、环境变量或相对路径。
3. 修改后说明真机默认值仍应指向 /home/eaibot。

## 5. 关于编译产物和运行环境

WSL 侧主要拷贝的是源码，不是完整运行环境。

因此默认不要依赖这些东西在 WSL 中完整可用：

1. build
2. devel
3. build_isolated
4. devel_isolated
5. 真机串口设备
6. 相机 USB 设备
7. 各类已经在比赛机本地配好的驱动

如果你需要判断一个改动是否合理，优先使用：

1. 静态读代码。
2. 检查 launch、yaml、TF、参数传递关系。
3. 做最小语法级检查。
4. 给出回到真机后的最小验证命令。

不要因为 WSL 跑不起来，就贸然断定代码逻辑有问题。

## 6. ROS 和真机相关判断原则

这套工程是 ROS Melodic 老工程，包含主车、机械臂、手眼标定、AprilTag、Astra 相机等链路。

凡是涉及下面这些内容，默认都要回到真机验证：

1. 机械臂运动。
2. 吸泵开关。
3. Astra 相机取流。
4. AprilTag 实时检测。
5. easy_handeye 标定采样。
6. 底盘 /cmd_vel 控制。
7. 雷达 /scan。
8. USB 摄像头索引。

WSL 侧 AI 可以做的，是提前把控制点、参数入口、风险点、验证步骤说清楚。

## 7. 机械臂相关特别注意事项

当前机械臂工程不是纯仿真工程，而是真机工程。

已知关键事实：

1. 机械臂主工作区是 /home/eaibot/mirobot_ws。
2. 手眼标定和抓取脚本主工作区是 /home/eaibot/handeye-calib。
3. 抓取脚本 mirobot_pick_test.py 按当前工程习惯应使用 python2。
4. 默认 ROS 环境顺序通常是先 source /opt/ros/melodic/setup.bash，再 source mirobot_ws，再 source handeye-calib。
5. 机械臂和吸泵串口当前依赖系统稳定 by-path，不建议为了 WSL 适配去改真机默认串口路径。

因此：

1. 不要为了让 WSL 里假想运行通过，擅自改机械臂串口默认值。
2. 不要因为 WSL 没有真实设备，就删掉真机驱动逻辑。
3. 改抓取逻辑、位姿生成、参数默认值时，要显式提醒用户做 dry-run 或最小动作验证。

## 8. 主车相关特别注意事项

主车代码主目录是 /home/eaibot/robocom_ws/src。

这里面既有 ROS 包，也有直接运行的 Python 脚本，还有模型权重和本地 yolov5 依赖。

注意：

1. 有的脚本直接使用 cv2.VideoCapture。
2. 有的脚本依赖 ROS 图像话题。
3. 有的脚本写死了摄像头索引，例如 0 号和 2 号。
4. 有的脚本依赖本地模型文件和 yolov5-master。

因此不要仅凭 WSL 中“没有摄像头画面”就判断主车逻辑错误。

这类修改更适合：

1. 在 WSL 中做代码重构、参数整理、路径梳理。
2. 回到真机后再验证摄像头、雷达、/cmd_vel 和模型加载。

## 9. 文档处理要求

当前 /home/eaibot/zcy 下的中文说明文档非常重要，WSL 侧 AI 必须优先参考，包括但不限于：

1. zcy/AI接手提示词.md
2. zcy/记忆.md
3. zcy/机械臂操作.txt
4. zcy/睿抗比赛机工程AI速览.md
5. zcy/代码功能表.txt

如果你改了代码入口、运行方式、默认参数、关键路径、串口路径或验证步骤，最好连同这些说明一起更新。

不要只改代码，不改说明。

## 10. 默认输出方式

当你完成一次修改建议或代码改动后，建议按下面格式向用户说明：

1. 改了什么文件。
2. 真正控制行为的入口在哪里。
3. 为什么这样改。
4. 哪些检查可以在 WSL 做。
5. 哪些验证必须回到这台机器做。
6. 需要把哪些文件同步回 /home/eaibot。

## 11. 一句话原则

在 WSL 里负责“看清楚和改明白”，在这台机器上负责“真机执行和最终验证”。
